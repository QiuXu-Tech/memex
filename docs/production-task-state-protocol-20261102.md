# Three-session task-state replay: registered protocol

This protocol was frozen before the issue-solving calls. It is a separate study of 30 public, historically discussed issues from 30 previously unused repository owners. Each task has a fixed issue snapshot, pinned repository snapshot and issue-specific acceptance criterion in the [registration](assets/benchmarks/production-task-state-20261102/registration.json). The [source manifest](assets/benchmarks/production-task-state-20261102/source-manifest.json), [selection record](assets/benchmarks/production-task-state-20261102/source-selection.json), and [review plan](assets/benchmarks/production-task-state-20261102/review-plan.json) preserve the screening and blind-review rules. The source snapshots and full responses remain local; the public manifest includes their hashes and issue links.

Each task uses randomized arm order. Both arms receive the same issue and pinned source through an isolated, read-only tool server, staged portions of the discussion, and access to their own earlier handoffs. Each arm uses three separate Claude Code sessions. The treatment also has Memex hooks and its four default MCP tools. A pair is complete only when all six sessions produce successful nonempty responses in distinct sessions. The first two randomly selected tasks are an infrastructure and spending check; remaining tasks use the same frozen protocol. Failures and missing sessions are retained.

The final outputs are engineering triage, not patches: they should discuss the reported behavior, relevant source and discussion evidence, uncertainty, and a next check. Two AI models independently score anonymous outputs against the frozen criterion; a third model rechecks differences in scores or unsupported-claim findings. Invalid, absent or truncated reviews do not become scores. Anonymous packet hashes and salted label commitments will be published before any task review; labels are opened only after review.

This is a compressed replay of real public issue histories. Source snapshots may postdate the discussion, and public material may have appeared in model training. It is not an online production experiment, a verified code fix or a human evaluation. Presence of a memory write or read does not by itself prove the answer depended on it. The agent-client list-price reservation is a spending guard, not an APIMaster invoice; failed calls, missing usage and other costs remain separate and may be unknown.
